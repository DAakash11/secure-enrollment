# Secure Device Enrollment & Firmware Signing Service

A Java-based service that models how devices are provisioned with cryptographic
identities and served signed firmware — with the Certificate Authority's private
key protected inside a Hardware Security Module (HSM). Inspired by real
device-provisioning and image-signing pipelines.

> **Status:** Actively developed as a study/portfolio project. The cryptographic
> core (PKI + HSM), token-based authentication, mutual-TLS device authentication,
> and a device-management (CRUD) API are complete and tested.

---

## What it demonstrates

- **PKI** — a Certificate Authority that issues X.509 certificates from
  Certificate Signing Requests (CSRs), with a verifiable chain of trust.
- **HSM integration** — the CA's private key is generated **inside** a SoftHSM2
  token and is **never extractable**. Signing happens in the token; the key
  never enters application memory.
- **Mutual TLS (mTLS)** — devices authenticate with **client certificates issued
  by the CA**, verified at the TLS handshake. The service reads the verified
  device identity directly from the presented certificate.
- **Token-based authentication** — a login endpoint issues short-lived JWTs
  signed with the **same HSM-protected key** (ES256).
- **PKCS#11 / JCA-JCE** — the HSM is accessed through Java's `SunPKCS11`
  provider and the standard `KeyStore` / `Signature` APIs.
- **Device management API** — a REST CRUD service over PostgreSQL for managing a
  device fleet, with a clean four-layer architecture and proper HTTP semantics.
- **Applied cryptography** — SHA-256, HMAC-SHA256, Base64 / Base64URL, hex —
  each verified against official test vectors (RFC 4231, standard SHA-256
  vectors).

## Architecture

**Certificate issuance (HSM-backed):**

```
Device                      Service (Spring Boot)                 SoftHSM2 Token
------                      ---------------------                 --------------
generate keypair
build CSR  ---------------> CertificateAuthority
(sign with own key)         - verify CSR signature
                            - build leaf certificate
                            - sign leaf  ---------------------->  CA private key
                                                                  (never leaves)
       leaf certificate <-- issued cert  <--------------------- signature only
verify against root CA
```

**Mutual TLS (device authentication at the transport layer):**

```
Device (client.p12)                         Service (HTTPS :8443)
-------------------                         ---------------------
present client cert  ---- TLS handshake ---> verify cert chains to CA root
                                             (truststore holds the CA root)
                     <------- established --- present server cert (CA-issued)
GET /whoami          -----------------------> read client cert from request,
                     <----- device identity -- return "device-001" (from the cert)
```

Both server and client certificates are issued by the same CA, so both sides
trust the same root. A client with no valid certificate cannot connect.

**Authentication (stateless, HSM-signed tokens):**

```
POST /auth/login  --> verify credentials (BCrypt) --> JWT signed ES256 in the HSM
Every /api/** request:  Authorization: Bearer <token>
                        --> JwtAuthFilter verifies signature + expiry
```

**Device management (layered):**

```
HTTP --> Controller --> Service --> Repository --> PostgreSQL
             |
             +-> @RestControllerAdvice (RFC 7807 error responses)
```

The CA holds only a **handle** to its private key (PKCS#11). All signing —
certificates and tokens — is delegated to the HSM.

```
src/main/java/com/aakash/qsec/
├── crypto/    # Hashing, HMAC, encoding utilities (verified vs test vectors)
├── ca/        # CertificateAuthority — CSR verification & certificate issuance
├── hsm/       # HsmKeyProvider (PKCS#11 access) + HsmInit (one-time key setup)
├── tls/       # TLS cert issuer (via the CA) + device-identity endpoint
├── auth/      # JWT service, login endpoint, token-validation filter
├── device/    # Device entity, repository, service, controller, error handling
└── ...        # Spring Security config
postman/       # Importable Postman collection for the API
```

TLS keystores (`tls/*.p12`) and private keys are **not** committed — they are
regenerated by running the TLS cert issuer against the HSM-backed CA.

## Running it

The app runs over HTTPS on port 8443 with mutual TLS required. Certificates are
generated from the CA (which signs inside the HSM):

1. Initialize the HSM key + root cert (one time): run `HsmInit`.
2. Issue the server and client certificates: run `TlsCertIssuer` (produces
   `tls/server.p12`, `tls/client.p12`) and build a truststore from the exported
   CA root.
3. Start the service: `./mvnw spring-boot:run`.

Every connection must present a valid client certificate:

```bash
# refused — no client certificate
curl --cacert tls/ca-root.pem https://localhost:8443/whoami

# accepted — client presents a CA-issued cert; server reports the device identity
curl --cacert tls/ca-root.pem --cert-type P12 --cert tls/client.p12:*** \
     https://localhost:8443/whoami
```

## Authentication

```
POST /auth/login    { "username": "...", "password": "..." }   -> { "token": "..." }
```

The token is a JWT signed with **ES256 using the HSM key**. Send it on every
request: `Authorization: Bearer <token>`. Tokens are short-lived (15 minutes);
the server verifies each with the HSM's **public** key.

## Device API

All endpoints require a valid JWT (and, at the transport layer, a client cert).

| Method | Path | Purpose | Success |
|--------|------|---------|---------|
| `POST` | `/api/devices` | Register a device | 201 Created |
| `GET` | `/api/devices` | List all devices | 200 OK |
| `GET` | `/api/devices/{id}` | Get one device | 200 OK |
| `PATCH` | `/api/devices/{id}/status` | Update status | 200 OK |
| `DELETE` | `/api/devices/{id}` | Remove a device | 204 No Content |

Errors follow **RFC 7807 (Problem Details)**: a missing device returns
`404 Not Found`; a duplicate serial or an illegal status change returns
`409 Conflict`.

**Domain rules (service layer):** serial numbers are unique; a `REVOKED` device
is terminal and cannot change status.

## Security design notes

- **Key never leaves the HSM.** The CA/signing key is generated in-token with the
  `never-extractable` and `always-sensitive` attributes set; verified directly
  with `pkcs11-tool`.
- **One protected key, three uses.** The same HSM key signs X.509 device
  certificates, the mTLS server/client certificates, and JWTs.
- **Certificate-based device auth.** With mTLS, a device's identity is its
  certificate — verified at the handshake, then read from the request. No
  password or token is needed to prove which device is connecting.
- **Proof of possession.** Before issuing a certificate, the CA verifies the
  CSR's own signature.
- **Stateless token auth.** No server-side sessions; passwords are checked only
  at login (BCrypt), not per request.
- **No secrets in source control.** Database password, HSM PIN, and TLS keystore
  passwords are supplied via environment variables. Private keys and keystores
  are gitignored.
- **Certificate hierarchy.** The root is a CA (`CA=true`, long-lived); issued
  leaves are not CAs (`CA=false`) and are short-lived (90 days).

## Testing

Tests are separated by type, chosen to match what each layer does:

- **Unit tests** — the crypto utilities (against published vectors such as
  RFC 4231), and the device service's business rules (mocked repository).
- **Integration tests** — the HSM access layer and Certificate Authority
  (against the real SoftHSM token via PKCS#11); and the REST controller
  (`@WebMvcTest` + MockMvc).

```bash
./mvnw test
```
